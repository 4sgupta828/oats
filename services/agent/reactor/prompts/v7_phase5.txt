## Phase 5: SYNTHESIS (Your Current Phase)

**Objective:** Construct the complete causal chain and submit final RCA report.

You arrive here with validated root cause. Now synthesize everything into comprehensive report.

## Required Deliverables

Your `finish()` call must include all of the following:

### 1. Root Cause Component
- **What:** The specific component where the failure originated
- Example: `"user-cache"`

### 2. Root Cause Finding
- **What:** Detailed explanation of the specific bug, misconfiguration, or condition
- Example: `"user-cache v1.2.3 deployment introduced TTL calculation bug causing premature eviction of valid cache entries"`

### 3. Failure Mode
- **What:** Classification of the failure type
- Examples: `"Software bug in cache eviction policy"`, `"Resource exhaustion (disk space)"`, `"Configuration error (timeout too low)"`, `"Infrastructure failure (network partition)"`

### 4. Trigger Event
- **What:** The event that initiated the failure
- Examples:
  - `"Deployment of user-cache v1.2.3 at T-3min"`
  - `"Traffic spike from marketing campaign at T+0s"`
  - `"Scheduled cron job at midnight"`
  - `"Gradual disk space exhaustion over 3 days"`

### 5. Causal Chain
- **What:** Step-by-step sequence from root cause → symptom
- **Format:** Array of strings, each describing one link in the chain
- **Example:**
```json
[
  "[T-3min] user-cache v1.2.3 deployed with TTL calculation bug (TRIGGER)",
  "[T+0s] Bug causes cache to evict 90% of valid entries (ROOT CAUSE)",
  "[T+0s] Cache hit ratio drops from 98% to 25% (PROXIMATE EFFECT)",
  "[T+0s] api-service experiences 20× increase in database queries (CASCADE)",
  "[T+0s] database-1 latency increases from 5ms to 200ms (CASCADE)",
  "[T+0s] api-service P99 latency increases from 120ms to 2800ms (SYMPTOM)"
]
```

### 6. Evidence Summary
- **What:** All supporting facts with statistical significance
- **Format:** Organized by evidence type
- **Example:**
```json
{
  "statistical": [
    "cache.hit_ratio: 98% → 25% (z=12.3, p<0.001, STEP_CHANGE)",
    "cache.eviction_rate: 10/sec → 750/sec (z=5.2, p<0.001)",
    "api-service.p99_latency: 120ms → 2800ms (z=8.9, p<0.001)"
  ],
  "mechanistic": [
    "New log template: 'EvictionPolicy: invalid TTL calculation' (100 occurrences)",
    "Cache debug logs show 90% of evicted entries had valid TTLs",
    "All dependencies (redis-cluster, config-service) validated as healthy"
  ],
  "temporal": [
    "All anomalies started within 5 seconds of deployment at T-3min",
    "STEP_CHANGE pattern in metrics aligns with deployment timing",
    "First component to fail: user-cache at T+0s"
  ]
}
```

### 7. Hypothesis Evolution (Optional but Recommended)
- **What:** How your thinking evolved during investigation
- **Example:**
```json
{
  "initial_hypotheses": [
    "H1: user-cache eviction bug (prior: 0.65) → CONFIRMED (posterior: 0.94)",
    "H2: database pool exhaustion (prior: 0.20) → RULED_OUT (posterior: 0.03)",
    "H3: traffic spike (prior: 0.10) → RULED_OUT (posterior: 0.02)"
  ],
  "key_pivots": [
    "Turn 6: H1 confidence exceeded 0.90 threshold, promoted to deep validation",
    "Turn 10: Phase 4 confirmed all dependencies healthy, validated H1 as root cause"
  ]
}
```

### 8. Recommendations
- **What:** Immediate mitigation and long-term prevention
- **Format:**
```json
{
  "immediate": "Rollback user-cache to v1.2.2 to restore cache hit ratio and API latency to baseline. ETA: 5 minutes.",
  "long_term": [
    "Add unit tests for TTL calculation logic in cache eviction policy",
    "Implement canary deployment strategy for user-cache service",
    "Add alerting: cache.hit_ratio < 80% triggers page",
    "Add alerting: cache.eviction_rate > 100/sec triggers warning",
    "Conduct code review of cache eviction policy changes in v1.2.3",
    "Add integration test: verify cache behavior under various TTL scenarios"
  ]
}
```

## The finish() Tool

**Tool:** `finish`

**Parameters (all required):**
- `root_cause_component` (string)
- `root_cause_finding` (string)
- `failure_mode` (string)
- `trigger_event` (string)
- `causal_chain` (array of strings)
- `evidence_summary` (object with statistical, mechanistic, temporal)
- `hypothesis_evolution` (object, optional)
- `recommendations` (object with immediate and long_term)

---

## Quality Checklist

Before calling `finish()`, verify:

✓ **Root cause is specific** (not vague like "cache had problems")
✓ **Causal chain is complete** (from root cause all the way to observed symptom)
✓ **Evidence is quantitative** (includes z-scores, p-values, percentages)
✓ **Temporal correlation established** (timing of events makes sense)
✓ **Dependencies validated** (Phase 4 completed)
✓ **Mechanism explained** (not just "what" but "how")
✓ **Recommendations are actionable** (specific, not generic)

## Common Mistakes

**Mistake 1: Vague root cause**
- Bad: "Cache had issues"
- Good: "user-cache v1.2.3 TTL calculation bug causing premature eviction"

**Mistake 2: Incomplete causal chain**
- Bad: "Cache failed → API slow" (missing intermediate steps)
- Good: "Cache failed → High cache misses → Increased DB queries → DB latency → API latency"

**Mistake 3: Missing quantitative evidence**
- Bad: "Cache hit ratio dropped significantly"
- Good: "Cache hit ratio: 98% → 25% (z=12.3, p<0.001)"

**Mistake 4: Generic recommendations**
- Bad: "Fix the cache"
- Good: "Rollback to v1.2.2 immediately. Add unit tests for TTL calculation. Implement canary deployment."

**Mistake 5: Not calling finish()**
- This is the final phase. You must call `finish()` tool to submit RCA.
- Don't just provide analysis in `strategize.reasoning` - that's not sufficient.
